# 1. Objective

Implement Kestrel's authoritative runtime topology model.

KES-004 must allow Kestrel to represent:

- physical compute devices;
    
- backend families;
    
- backend instances;
    
- physical memory spaces;
    
- relationships between devices and memory spaces;
    
- runtime-local identities;
    
- topology ownership and lifecycle;
    
- topology discovery;
    
- topology introspection.
    

The result must answer:

> What hardware exists, what execution systems exist, what memory exists, and how are they connected?

KES-004 must not decide what should execute where.

---

# 2. Core Concepts

## Device

A device represents actual physical compute hardware.

Examples:

- host CPU;
    
- Intel integrated GPU;
    
- AMD GPU;
    
- NVIDIA GPU;
    
- future accelerator/NPU.
    

Device classes:

- CPU
    
- GPU
    
- ACCELERATOR
    
- UNKNOWN
    

Important:

- CUDA is not a device.
    
- Vulkan is not a device.
    
- AVX2 is not a device.
    
- Scalar is not a device.
    

Do not introduce IGPU and DGPU as fundamental device classes.

Integrated/discrete behavior is represented through memory topology.

---

## Backend Family

A backend family identifies one execution implementation/API.

Frozen families:

- SCALAR
    
- AVX2
    
- VULKAN
    
- CUDA
    

This is a type of execution mechanism, not hardware.

---

## Backend Instance

A backend instance represents:

> one backend family attached to exactly one physical device.

Examples:

- Scalar + CPU
    
- AVX2 + CPU
    
- Vulkan + Intel GPU
    
- Vulkan + NVIDIA GPU
    
- CUDA + NVIDIA GPU
    

Required properties:

- runtime-local backend-instance ID;
    
- backend family;
    
- target device ID.
    

Multiple backend instances may target the same device.

One backend family may have multiple instances.

Example:

- Vulkan + GPU 0
    
- Vulkan + GPU 1
    

The same NVIDIA GPU may legitimately expose:

- Vulkan instance;
    
- CUDA instance.
    

---

# 3. Memory Spaces

A memory space represents where bytes physically live.

Kinds:

- SYSTEM
    
- DEVICE_LOCAL
    
- UNKNOWN
    

Examples:

- system RAM;
    
- NVIDIA GPU VRAM;
    
- AMD GPU VRAM.
    

Do not create:

- CUDA_MEMORY;
    
- VULKAN_MEMORY.
    

Those are execution APIs, not physical memory locations.

Multiple memory spaces of the same kind are legal.

Example:

- GPU 0 VRAM = DEVICE_LOCAL space A
    
- GPU 1 VRAM = DEVICE_LOCAL space B
    

They are not one combined memory space.

---

# 4. Device ↔ Memory Relationship

Kestrel must represent the physical relationship between a device and a memory space.

Relationship kinds:

- LOCAL
    
- SHARED
    
- REMOTE
    

Examples:

CPU → system RAM = SHARED

integrated GPU → system RAM = SHARED

discrete NVIDIA GPU → own VRAM = LOCAL

CPU → NVIDIA VRAM = REMOTE

NVIDIA GPU → system RAM = REMOTE

Important:

REMOTE describes physical topology only.

It does not mean:

> this backend can never access this memory.

Backend compatibility belongs to a later capability layer.

---

# 5. Runtime-Local IDs

Every topology object must have a runtime-local ID.

Required object identities:

- device ID;
    
- backend-instance ID;
    
- memory-space ID.
    

IDs must:

- be unique within one runtime topology;
    
- remain stable for the lifetime of that topology;
    
- not depend on object memory addresses;
    
- not be interpreted as persistent hardware identity.
    

Example:

Device ID 1 today is not guaranteed to represent the same physical GPU after program restart.

Persistent hardware identity is a separate later concern.

---

# 6. Device Metadata

A device may contain:

- runtime-local ID;
    
- device class;
    
- human-readable name;
    
- vendor information;
    
- trustworthy hardware identity data when available.
    

Do not place the following into the device object:

- supports FP16;
    
- supports BF16;
    
- supports matmul;
    
- supported tensor layouts;
    
- performance measurements;
    
- planner decisions;
    
- backend-specific resource limits.
    

Those belong to later layers.

For Kestrel v2, represent the host CPU as one physical device.

Do not model individual CPU cores as separate Kestrel devices.

---

# 7. Runtime Topology Registry

Implement one authoritative topology object conceptually containing:

runtime_topology

- devices[]
    
- backend_instances[]
    
- memory_spaces[]
    
- relationships[]
    

The topology owns all of these objects.

Subsystems may reference topology objects, but they do not independently own/free them.

Required lifecycle:

topology_init(...)  
topology_destroy(...)

Exact API spelling may be chosen during implementation as long as the architectural contract remains intact.

---

# 8. Ownership

runtime_topology owns:

- device descriptors;
    
- backend-instance descriptors;
    
- memory-space descriptors;
    
- relationship descriptors.
    

Destroying the topology destroys its topology metadata.

No topology object should outlive the registry that owns it.

Persistent relationships must use runtime-local IDs rather than public pointer identity.

Internal implementation may resolve IDs to pointers/references for efficiency.

---

# 9. Discovery Pipeline

Conceptual discovery order:

1. initialize empty runtime topology;
    
2. discover host CPU;
    
3. create Scalar + CPU backend instance;
    
4. detect AVX2 support;
    
5. if AVX2 is legal, create AVX2 + CPU;
    
6. discover Vulkan physical devices if Vulkan support is available;
    
7. create Vulkan backend instances;
    
8. discover CUDA physical devices if CUDA support is available;
    
9. create CUDA backend instances;
    
10. establish memory spaces and device-memory relationships;
    
11. deduplicate physical devices across APIs only when identity is trustworthy.
    

---

# 10. Scalar Baseline

Scalar + host CPU is the baseline Kestrel backend instance.

Unless runtime initialization fundamentally fails, a valid supported environment should expose:

- one host CPU device;
    
- one Scalar backend instance targeting it.
    

Scalar is the correctness/reference execution path.

---

# 11. AVX2 Discovery

Do not assume AVX2 merely because Kestrel was compiled on x86.

AVX2 backend instance exists only if runtime capability detection confirms the CPU supports it.

Therefore:

compiled AVX2 code  
≠  
runtime AVX2 availability

---

# 12. Optional Backend Failure

Failure to discover an optional backend must not destroy the entire runtime.

Examples:

- CUDA unavailable;
    
- no NVIDIA GPU;
    
- Vulkan loader unavailable;
    
- no Vulkan-compatible GPU.
    

These must not prevent Scalar CPU execution.

Optional discovery should fail recoverably.

---

# 13. Cross-API Device Deduplication

If:

Vulkan discovers an NVIDIA T4

and

CUDA discovers an NVIDIA T4

Kestrel should ideally produce:

one physical device

plus

two backend instances.

However:

never deduplicate purely because names match.

Example:

"NVIDIA RTX 4090"

is insufficient by itself to prove two API discoveries refer to the same physical card.

Rules:

- strong identity → merge;
    
- uncertain identity → keep separate;
    
- false duplication is acceptable;
    
- false merging is not.
    

Conservative duplication is safer than incorrect identity.

---

# 14. Compile-Time vs Runtime State

Compile-time state describes what Kestrel was built with.

Example:

- Scalar compiled;
    
- AVX2 compiled;
    
- Vulkan compiled;
    
- CUDA compiled.
    

Runtime state describes what actually exists.

Example:

- host CPU detected;
    
- AVX2 supported;
    
- two Vulkan GPUs found;
    
- no CUDA device found.
    

These concepts must remain separate.

CUDA support compiled into Kestrel does not imply:

> CUDA hardware exists.

---

# 15. Introspection

Provide a developer-visible topology dump/introspection mechanism.

It should make the discovered machine understandable.

Example:

Devices:  
[0] Intel Core i7 — CPU  
[1] NVIDIA T4 — GPU

Memory Spaces:  
[0] System RAM — SYSTEM  
[1] T4 VRAM — DEVICE_LOCAL

Backend Instances:  
[0] Scalar → Device 0  
[1] AVX2 → Device 0  
[2] Vulkan → Device 1  
[3] CUDA → Device 1

Relationships:  
Device 0 ↔ Memory 0 : SHARED  
Device 1 ↔ Memory 1 : LOCAL  
Device 1 ↔ Memory 0 : REMOTE

The format does not need to match this example exactly.

The information does.

---

# 16. Required Invariants

The implementation must preserve all of these:

1. Device means physical compute hardware.
    
2. Backend family means execution implementation/API.
    
3. Backend instance binds exactly one backend family to exactly one device.
    
4. Multiple backend instances may target one device.
    
5. One backend family may have several runtime instances.
    
6. CUDA is never represented as a physical device.
    
7. AVX2 is never represented as a physical device.
    
8. Memory spaces represent physical memory.
    
9. Backend/API identity does not define memory-space identity.
    
10. Multiple physical memory spaces of the same kind may exist.
    
11. Runtime topology owns topology-object lifetimes.
    
12. Topology objects use runtime-local IDs.
    
13. Runtime IDs are not persistent machine IDs.
    
14. Hardware deduplication requires trustworthy identity.
    
15. Name equality alone is insufficient for deduplication.
    
16. Topology does not contain operation-support information.
    
17. Topology does not contain performance data.
    
18. Topology does not make planner decisions.
    
19. Optional backend discovery failure is recoverable.
    
20. Scalar + host CPU is the baseline backend instance.
    
21. Physical memory accessibility is distinct from backend/storage compatibility.
    

---

# 17. Explicitly Out of Scope

Do not implement any of the following in KES-004:

- storage_t allocation;
    
- host storage provider;
    
- CUDA memory allocation;
    
- Vulkan buffers;
    
- tensor allocation;
    
- tensor migration;
    
- automatic transfers;
    
- capability matrices;
    
- matmul support checks;
    
- dtype/backend legality checks;
    
- kernel dispatch;
    
- performance benchmarking;
    
- persistent performance profiles;
    
- planner;
    
- automatic backend selection;
    
- execution scheduling;
    
- autodiff;
    
- neural-network operators.
    

If one of these becomes necessary while writing KES-004, stop and reconsider the boundary before adding it.

# 18. Test Requirements

At minimum, tests must prove:

## CPU baseline

Initialization discovers:

- exactly one logical host CPU device;
    
- a Scalar backend instance targeting it.
    

---

## Runtime IDs

All registered objects receive valid unique IDs within their own object class.

Relationships resolve to valid object IDs.

---

## Ownership

Topology destruction releases all topology-owned metadata without leaks.

Destroying an empty/partially initialized topology must be safe according to the lifecycle contract you define.

---

## Backend binding

Every backend instance references exactly one valid device.

---

## AVX2

On AVX2-capable hardware:

AVX2 + CPU is created.

On non-AVX2-capable hardware or simulated negative detection:

it is not created.

---

## Optional backend failure

Simulated Vulkan/CUDA discovery failure must leave the valid CPU topology usable.

---

## Multiple backend instances

A synthetic topology must be able to represent:

one physical GPU

with both:

- Vulkan backend instance;
    
- CUDA backend instance.
    

---

## Multiple devices

A synthetic topology must support multiple GPUs.

Example:

GPU A  
GPU B

with independent backend instances and memory spaces.

---

## Memory topology

Tests must represent at least:

CPU + shared system RAM

integrated GPU + shared system RAM

discrete GPU + local VRAM

---

## Device deduplication

Tests must prove:

- strong matching hardware identity can merge duplicate discovery records;
    
- ambiguous/name-only identity does not force a merge.
    

---

## Introspection

Topology dump/introspection must correctly report a synthetic topology.

---

# 19. Acceptance Criteria

KES-004 is complete only when:

- runtime topology initializes successfully on a CPU-only environment;
    
- Scalar + CPU appears;
    
- AVX2 appears only when runtime support exists;
    
- topology supports multiple devices;
    
- topology supports multiple backend instances per device;
    
- topology supports multiple memory spaces;
    
- device-memory relationships are explicit;
    
- runtime-local IDs are stable during topology lifetime;
    
- optional backend discovery failure is recoverable;
    
- cross-API deduplication does not rely on device names alone;
    
- introspection output describes the topology coherently;
    
- all tests pass;
    
- memory analysis reports no topology leaks;
    
- no capability/performance/planner logic has leaked into this ticket.

# Engineering Note

KES-004 is not supposed to make Kestrel smart yet.

It gives Kestrel something more fundamental:

> eyes.

After this ticket, Kestrel should be able to look at a machine and say:

“I see one CPU, two GPUs, three memory spaces, and these execution mechanisms are attached to these devices.”

Later tickets teach it:

“What can they do?”

Then:

“How well do they do it?”

Then:

“What should I choose?”

But KES-004 only builds the map.

Do not build the navigator before the map exists.
