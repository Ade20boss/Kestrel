## Context

Kestrel now has a frozen dtype architecture.

We explicitly separate three concepts:

```
PROMOTION
What common dtype should operands use?

ACCUMULATION
What dtype should repeated arithmetic build up into?

OVERFLOW
What happens when the chosen dtype still cannot represent the result?
```

These are related, but they are not the same thing.

KES-003 implements the dtype identity/query layer and the promotion/accumulation rules.

It does **not** implement arithmetic kernels yet.

---

# Objective

Implement the permanent Kestrel dtype subsystem so every later layer can ask:

```
Is this dtype valid?

How many bytes does one element occupy?

Is it floating point?

Is it integer?

Is it BOOL?

Is it a signed integer?

Is it an unsigned integer?

What dtype do these operands promote to?

What dtype should this numeric type accumulate into?
```

These answers must be defined centrally by Kestrel and must not depend on the backend.


# 5. Dtype size

`kestrel_dtype_size()` returns the physical byte width of one element.

Frozen values:

```
BOOL    → 1 byte

FP16    → 2
BF16    → 2
FP32    → 4
FP64    → 8

INT8    → 1
UINT8   → 1

INT16   → 2
UINT16  → 2

INT32   → 4
UINT32  → 4

INT64   → 8
UINT64  → 8
```

The enum value itself must not encode the byte size.

There is **no separate integer-width table required**.

When integer bit width is needed internally:

```
width_bits = dtype_size(dtype) × 8
```

because size already gives us the required information.

# 7. Promotion semantics

Promotion answers:

> What common dtype should operands use?

Promotion does **not** guarantee the arithmetic result can never overflow.

For example:

```
FP16 + FP16 → FP16
```

can still overflow FP16.

Overflow is a separate rule.

Promotion should be symmetric:

```
promote(A, B) == promote(B, A)
```

whenever promotion is legal.

---

# 8. Floating-point promotion

Same type remains itself:

```
FP16 + FP16 → FP16
BF16 + BF16 → BF16
FP32 + FP32 → FP32
FP64 + FP64 → FP64
```

Mixed floats:

```
FP16 + BF16 → FP32

FP16 + FP32 → FP32
BF16 + FP32 → FP32

FP16 + FP64 → FP64
BF16 + FP64 → FP64
FP32 + FP64 → FP64
```

Reason for:

```
FP16 + BF16 → FP32
```

Neither 16-bit format is universally superior to the other.

They trade range and precision differently.

FP32 is the common Kestrel arithmetic type.

---

# 9. Integer promotion

Promotion uses:

```
size
signedness
```

No separate width metadata is needed.

---

## Same signedness

Use the wider dtype.

Examples:

```
INT8 + INT16 → INT16
INT16 + INT64 → INT64

UINT8 + UINT32 → UINT32
UINT16 + UINT64 → UINT64
```

---

## Mixed signed and unsigned

Let:

```
S = signed operand
U = unsigned operand
```

### Signed operand wider than unsigned

Use the signed dtype.

```
INT16 + UINT8 → INT16
INT32 + UINT16 → INT32
INT64 + UINT32 → INT64
```

---

### Same width

Use the next wider signed dtype.

```
INT8 + UINT8 → INT16
INT16 + UINT16 → INT32
INT32 + UINT32 → INT64
```

---

### Unsigned operand wider

Use a signed dtype wider than the unsigned dtype.

```
INT8 + UINT16 → INT32
INT16 + UINT32 → INT64
```

---

### No wider signed dtype exists

Promotion is invalid.

```
INT64 + UINT64 → INVALID

INT32 + UINT64 → INVALID
INT16 + UINT64 → INVALID
INT8 + UINT64 → INVALID
```

Kestrel must not silently choose `UINT64`.

An explicit cast is required.

---

# 10. Integer + floating-point promotion

Rule:

> Choose the smallest floating dtype that can exactly represent the integer domain while being at least as capable as the existing float operand.

## 8-bit integers

```
INT8/UINT8 + FP16 → FP16
INT8/UINT8 + BF16 → BF16
INT8/UINT8 + FP32 → FP32
INT8/UINT8 + FP64 → FP64
```

## 16-bit integers

```
INT16/UINT16 + FP16 → FP32
INT16/UINT16 + BF16 → FP32
INT16/UINT16 + FP32 → FP32
INT16/UINT16 + FP64 → FP64
```

## 32-bit integers

```
INT32/UINT32 + FP16 → FP64
INT32/UINT32 + BF16 → FP64
INT32/UINT32 + FP32 → FP64
INT32/UINT32 + FP64 → FP64
```

FP32 cannot exactly represent every 32-bit integer.

## 64-bit integers

```
INT64/UINT64 + any float
→ INVALID implicit promotion
```

No supported float exactly represents the full 64-bit integer domain.

Explicit conversion required.

---

# 11. BOOL promotion

BOOL does not participate in numeric promotion.

Invalid numeric combinations:

```
BOOL + BOOL
BOOL + INT32
BOOL + FP32
```

BOOL is reserved for:

```
comparisons
logical operations
masks
```

Numeric comparison results may produce BOOL.

Turning BOOL into a numeric value requires explicit conversion.

---

# 12. Accumulation semantics

Accumulation means repeated arithmetic such as:

```
sum
dot product
matmul
convolution
reductions
```

Accumulation widening reduces numerical risk.

It does **not** guarantee overflow becomes impossible.

---

## Floating accumulation

```
FP16 → FP32
BF16 → FP32
FP32 → FP32
FP64 → FP64
```

---

## Signed integer accumulation

```
INT8  → INT32
INT16 → INT64
INT32 → INT64
INT64 → INT64
```

---

## Unsigned integer accumulation

```
UINT8  → UINT32
UINT16 → UINT64
UINT32 → UINT64
UINT64 → UINT64
```

---

## BOOL accumulation

No generic numeric accumulation dtype.

---

# 13. Mixed-type accumulation

Do not create a separate mixed accumulation matrix.

Use:

```
STEP 1
Promote the operand types.

STEP 2
Take the accumulation dtype of the promoted type.
```

Example:

```
INT8 + UINT8
↓
promotion = INT16
↓
accumulation = INT64
```

Another:

```
FP16 + FP32
↓
promotion = FP32
↓
accumulation = FP32
```

---

# 14. Output dtype rules

Ordinary arithmetic:

```
output dtype = promoted dtype
```

Example:

```
FP16 + FP32 → FP32 output
```

Accumulation-heavy operation:

```
output dtype = accumulation dtype
```

Example:

```
sum(FP16)
→ FP32 accumulation
→ FP32 output
```

```
dot(INT8, INT8)
→ INT32 accumulation
→ INT32 output
```

Any narrowing afterward must be explicit.

---

# 15. Overflow semantics

Overflow is separate from promotion and accumulation.

KES-003 does not implement arithmetic kernels yet, but the semantics are frozen here.

---

## Floating-point overflow

Floating arithmetic follows IEEE-style behavior.

Finite overflow:

```
→ +INF / -INF
```

Invalid floating operations:

```
→ NaN where appropriate
```

No automatic saturation.

---

## Integer overflow

Kestrel does not inherit undefined C signed-overflow semantics.

Integer arithmetic uses deterministic fixed-width modular wraparound.

Conceptually:

```
N-bit integer arithmetic
→ modulo 2^N
```

Examples:

```
INT8:
127 + 1 → -128
```

```
UINT8:
255 + 1 → 0
```

Later backend arithmetic code must implement this without relying on undefined signed overflow in C.

---

## Accumulator overflow

If an accumulator itself overflows:

```
integer accumulator
→ integer wraparound rule
```

```
floating accumulator
→ IEEE-style floating overflow rule
```

Widening reduces risk but does not eliminate it.

---

# 16. Explicit conversions

Implicit widening is allowed according to promotion.

Implicit narrowing is not.

Examples requiring explicit conversion:

```
FP32 → FP16
FP64 → FP32

INT64 → INT16
UINT32 → UINT8

INT64 → FP64
UINT64 → FP64
```

Potential information loss must be visible.

# Required invariants

1. Every supported dtype has exactly one identity.
2. `INVALID` is zero.
3. `COUNT` is not a valid dtype.
4. Enum values do not encode size.
5. Size is deterministic.
6. Integer bit width is derived from size rather than duplicated.
7. Classification is deterministic.
8. Signedness applies only to integer dtypes.
9. Promotion is global Kestrel policy.
10. Promotion is symmetric.
11. Promotion does not promise overflow cannot happen.
12. Accumulation is distinct from promotion.
13. Accumulation widening does not promise overflow cannot happen.
14. BOOL does not silently become numeric.
15. Lossy narrowing is never implicit.
16. Backends cannot redefine promotion.
17. Backends cannot redefine accumulation.
18. Integer overflow semantics are deterministic.
19. Floating overflow semantics are globally defined.
